# 结构与关系图

## 使用场景
系统架构、概念边界、能力封装、共享资源、角色分工，以及模型组件的静态关系。

## 工作规格
保留对象、对象类型、边界和有类型的关系。区分已证实关系、设计提案与尚未明确的关系。
不要默认“对象都列出来”就等于解释完成；核心交付是读者可以正确复述它们之间的关系。

| 语义 | 表达 |
|---|---|
| 包含、所属、作用域 | 边界或嵌套；边界名称说明其含义 |
| 调用、控制、交接 | 有方向、必要时带动词的连线 |
| 数据输入输出、读写 | 单独标明流动对象或访问语义，避免误读为控制关系 |
| 多方共享一个资源 | 多方分别连接该资源，不补上参与者之间的直连 |
| 并行、互补 | 同组并列；仅存在实际交互时连线 |
| 部分交叠 | 仅在交集有实际含义时使用重叠区域 |
| 不同抽象层级 | 分层或分区；不要强制画成同层等价模块 |

不同关系可以共存。布局不能用一种箭头概括所有关系，也不能为了避免串联就退回毫无关系说明的平铺。
算法、确定性工作流、Agent、存储与权限边界应能区分；不因它们都参与 AI 系统就全部画成 Agent。
视图层级必须服务当前问题。总览保留外部系统和关键连接，局部图再展开内部机制。

## 锚定案例：两个参与者与两个仓库
两个参与者都可读写上下文仓库和代码仓库，但两者不直接通信。
最小完整结构是四个对象、四组标为“读/写”的访问关系；不画参与者之间的直连，不省略代码仓库。
“读/写”可以用带标签的访问线表示；不要让双向箭头被误读为仓库主动调用参与者。
未说明的仓库间同步关系保持未画出；不要为视觉对称而补造。

## 验收
隐藏说明文字后，分组、连线和方向是否仍然暗示正确关系？
读者会不会把部署边界当权限边界，把共享资源当代理通信，把相邻模块当先后步骤？
