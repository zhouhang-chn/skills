# Visual Explain

## 目标
让读者通过图形看懂一个问题。先确定内容与关系，再选择视觉表达；不以套用图形模板代替理解。

## 开始前
从当前讨论提取读者、用途、核心问题、必须保留的信息、禁止误解和交付形式。信息足够就直接执行，不要求用户填写表格。
只澄清会改变结论、关键关系或交付物的缺口。用户的探索性疑问是待验证假设，不自动成为新的硬约束。
要修改具体图片，先取得实际可用的目标；优先检索可访问的已有文件，仍不可用再索取。不要假定历史图片或不透明 ID 就是可编辑目标。
使用已有证据；外部事实缺失时查相应来源，当前版本、日期、性能等易变事实必须核实。区分事实、重构与建议，不把漂亮的图当成证据。

## 按需选择配方
只读取主任务对应的一个文件；确有必要时增加一个辅助配方，不默认加载全部。

| 读者的问题 | 配方 |
|---|---|
| 有哪些对象？彼此是什么关系？ | [structure](references/structure.md) |
| 谁做什么？如何推进、判断与结束？ | [process](references/process.md) |
| 哪些不同？如何演进？怎样进入下一阶段？ | [comparison-evolution](references/comparison-evolution.md) |
| 怎样理解、学会或迁移一个概念？ | [teaching](references/teaching.md) |
| 数据、数量、位置或证据究竟说明什么？ | [evidence](references/evidence.md) |

组合任务只保留一个主阅读结构。例如“展示流程，并体现前后变化”，以同一流程为主，把变化标在对应步骤。

## 执行
1. 写出简短工作规格：核心问题；关键对象/状态/数值；关系或变换；必须保留与禁止出现的内容；证据边界。开放性问题可以呈现分歧，不必制造结论。
2. 检查语义：关系类型、方向、边界、数量、条件和来源。只有关联时，不画成调用；只有时间先后时，不画成继承；没有关系时，不为连通画面补线。
3. 选择能直接表达关系的视觉结构。包含、并行、流转、依赖、对照与坐标各有含义；空间位置、尺寸和线型也不能暗示不存在的关系。
4. 给核心机制最大的视觉权重，收起次要背景。简化先删重复、装饰和次要连线，保留解释所需的最小完整结构。
5. 按宿主规则调用实际渲染工具。关系图、概念图和解释性插画默认用可用的原生图像生成；精确数据、计数、坐标或几何用确定性计算/绘图保证准确。显式指定的工具与交付约束优先。
6. 检查实际可访问的成图，按规格修正；最后检查交付形式和显示效果。无法看见实际像素时，只报告已完成的规格/文件检查，不声称做过视觉验收。

## 视觉约束
- 每张图有一个主问题，标题、中心视觉和注释都服务它。密集说明可拆成总览与局部，不能靠缩小字体装进一张图。
- 文字保留名称、关系、条件和关键解释；不把长段落装进卡片，也不为极简删成无法独立理解的关键词。
- 技术解释默认克制配色、清楚分组、足够留白；颜色与线型的意义保持一致。专业感来自层级和排版，不靠彩虹配色或装饰图标。
- “更有设计感”不等于增加节点、渐变或立体装饰。不要默认交付原始 Mermaid 式方框箭头图；用户明确要 Mermaid/可编辑源时按要求提供。
- 构图指令与图中文字分开。“左侧约三分之一”“突出主干”“第一个版本”等制作说明不得漏进画面，除非它本身就是内容。
- 沿用用户要求的语言；保留必要技术名称，不无端中英重复。以真实阅读尺寸检查标题、关键标签和线条，而非只看放大图。

## 按反馈迭代
先判断反馈针对语义、内容范围、层级、布局、文字量、风格还是交付；只在必要范围内修改。
“漂亮一点”冻结语义；“简单一点”保留必要对象与关系；“关系不对”先修模型再布局，不能只换位置。
将已确认的纠正保留为本轮不变量；新要求明确改变旧决定时更新基线，不能同时保留互相矛盾的约束。
针对新反馈修正后，回查此前纠正过的错误，防止换版回退。若仍有误读风险，优先改变结构，而非增加免责声明。

## 交付验收
读者能否说清核心问题？必要对象/条件是否齐全？是否出现错误关系或无依据结论？实际尺寸是否可读？
交付用户要求的实际图片或图形文件，不用提示词、代码块或内部路径冒充成图；文件链接必须指向真实存在的产物。
用户只要图时，不附长篇复述；遵守宿主对生成后回复的规则。未请求时，不自动加做文档、幻灯片、发帖或提交仓库。
